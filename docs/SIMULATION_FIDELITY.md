# 一致性与比赛模式说明

## 实现中能够确认的部分

`native/desktop_host.cpp` 构造并读取比赛输入，执行原版开赛准备，再逐步调用原版详细比赛推进函数，直到自然终场。当前适配构建的推进入口为 `0x4520bd0`；地址仅描述本适配版本，不能作为其他构建的接口。

宿主使用原版内部的基准比赛派生类和对应线程上下文承载推演。它并未启动正常游戏界面的手打、度假或即时结果任务，也不能仅凭调用了详细循环就认为整个游戏外围流程均已复现。

正常比赛推进会产生球员动作、进球与罚牌，整场推演使用原生结果和统计对象。PKM 用于装载输入背景，比赛在此基础上重新运行。

`src/fm27_profiles.py` 与服务端的输入标准化会统一开赛状态；比赛配置和存档球队载入流程也会改变实验输入。只有完整输入、随机状态、比赛背景与临场操作均得到对齐后，才具备开展严格游戏内配对验证的条件。

## 现有证据分别说明什么

| 证据 | 能支持的结论 | 范围限制 |
| --- | --- | --- |
| 原版初始化、准备、详细推进和自然结束调用链 | 工具使用原版详细比赛计算 | 不能证明外围游戏流程全部相同 |
| 输入准备后的原生回读校验 | 已接入字段按要求写入并通过核验 | 不能证明与职业生涯当天完整输入相同 |
| 历史固定输入、固定种子的重复运行 | 在已测配置下能够复现结果 | 不代表所有输入、版本和机器均已验证 |
| 历史 12 场独立宿主与复用宿主配对，比分、球队统计及进球、助攻、罚牌事件一致 | 该固定样本下宿主复用没有改变所比较的结果 | 是两种工具运行方式之间的比较，双方均不是游戏界面 |
| 此前源码整理时的编译、预检、HTTP 服务和 EXE 自检通过 | 源码整理后的构建和启动链可用 | 本次源码发布准备没有重新跑完整比赛，更没有执行游戏内配对 |

历史原始证据位于维护者研究工作区的 `FM27_STANDALONE_STATUS_ZH.md`、`desktop_app/warm_integration_20261103/ACCEPTANCE.json` 和 `desktop_app/state_research/快速与详细模拟说明.md`，不包含在公开源码包中。上述说明按这些记录的原有范围表述，不把历史样本当成当前所有功能的全面验证。

## 三种游戏入口的结论

当前工具运行详细比赛计算；用户界面不包含比赛中的临场指挥流程。按计算粒度可以描述为接近手打所对应的详细模拟，但不能称为手打全流程复现。

需要区分“详细比赛计算”和“画面展示”：后台完整模拟也可以执行详细比赛循环，隐藏画面并不意味着切换算法。之前代码分析确认了后台详细任务调用完整比赛循环的情况，同时也找到了独立简化模型。因而不能把所有名为“跳过”的入口都归入简化模型，也不能把所有“跳过”入口一概认作详细模型。判断某个具体按钮，需要对应版本的调用链。

尚未闭合 FM27 手打、度假、跳过／即时结果三个入口到任务工厂和比赛循环的全部路径，也未完成同一比赛的游戏内配对。因此，三种入口的结果等价性均不作承诺。其他版本中的入口研究不能直接套用于 FM27。

本工具的快速模式只调整事件采集和核验范围；宿主仍调用相同的详细比赛推进函数。这里的“快速”不能作为判断原版游戏按钮含义的依据。

## 今后如何验证与游戏内的一致性

需要固定准确游戏构建，捕获同一场比赛的完整开赛输入和随机状态，明确临场操作及助教决策策略，再分别通过游戏入口与本工具运行。比较应覆盖输入回读、逐时比分及事件、球队统计、终场状态，并包含多种球队和比赛情境。

在完成这类配对前，只报告已测项目与样本，不给出笼统的一致率，也不承诺逐球或比分完全复现。
