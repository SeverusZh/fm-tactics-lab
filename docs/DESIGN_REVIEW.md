# 整体设计评审

本评审针对用户反馈的六项问题：FMF 无法导入、存档战术无法导入战术板与球员属性、存档页操作无意义、设置页无真实交互、实验页难以理解、球员属性无法单独修改。评审基于 v2 实现、v1 功能矩阵与 Windows 实机验证，结论与后续计划记录在此。

## 一 结论

v2 的领域层、仓储、HTTP 与前端骨架已经完整，但产品层没有闭环：入口藏在错误页面、内部工具字段直接暴露给用户、关键动作缺少预览与反馈、需要外部资源的能力没有任何可见的配置路径。六项反馈归为三个根因。

第一，信息架构错位。导入存档、导入 FMF 属于战术与球员工作流的入口，却全部挂在存档库里；运行实验同时出现在底部运行栏、实验页与任务页；设置页只有内部键值编辑器。

第二，能力缺口被静默吞掉。真实 FMF 是 AFE 归档，必须由与本机游戏版本匹配的原生宿主解析；v2 只能读写自定义 FMFV2 JSON，且从未把游戏目录交给宿主，因此真实 FMF 必然失败并显示“FMF 文件无效”。存档战术库、定位球编辑在 v2 中整体缺失。玩家属性只能整队批量覆盖，没有单项编辑。

第三，缺少配置与诊断闭环。engine_root 只能由命令行或环境变量提供，桌面壳固定指向数据目录下的 engine；游戏目录完全不存在。用户在设置页没有任何办法让引擎可用，也没有任何地方能看到走到哪一步失败。

在这三个根因之外还有一层资源事实，决定了能力能否可用。原生宿主必须与本机游戏的 game_plugin.dll 版本匹配，否则以 PE 布局不兼容退出；宿主解析 FMF 与 TAC 前要先加载比赛 fixture 与游戏共享资源，因此引擎工作区至少需要 fm27_native 下的宿主、版本声明、编辑器快照与 fixtures，加 fm27_research 的定位球枚举，再加场景目录 catalog.json。安装包不能分发游戏资源与宿主二进制，所以应用必须提供把这些资源导入本地数据目录的路径，而不是假设它们已经存在。

## 二 目标信息架构

一级导航收敛为六项：战术板、球员、存档、实验、结果、设置，外加独立的帮助页。每页只有一个主行动，其余为次要操作。

能力分层必须显式：不依赖外部资源的能力在首次启动即可用，包括新建空白战术、编辑阵型与指令、导入导出方案、浏览球员属性、按名单新建草案；依赖游戏安装的能力在未配置时显示明确原因与跳转设置，包括真实 FMF 读写、存档战术解析、真实比赛批次。

## 三 本轮交付

引擎与资源闭环。设置页提供引擎目录与游戏目录两项真实配置，支持原生目录选择器，保存后写入数据库并提示重启侧车；侧车启动时按命令行显式值、数据库存储值、环境变量、数据目录默认值的顺序解析。引擎诊断调用宿主镜像检查，展示兼容声明、原因、适配器版本与镜像指纹。设置页可重启侧车，等待健康检查恢复，超时给出取消与重试出口。引擎资源导入支持从旧版安装目录或资源包发现工作区，按游戏镜像哈希优先选择匹配的宿主，逐项复制宿主、版本声明、编辑器快照、fixtures、定位球枚举与场景目录，并报告缺失文件。

真实 FMF 读写。导入按文件头区分自定义格式与游戏归档，游戏归档交给原生宿主解码，读取事件中的心态、球队位域、双阶段对应关系与 22 个位置单元，再按 v1 的映射规则生成双阶段场景并建草案；未配置引擎时返回明确错误与设置入口。导出以服务端模板场景为基础，只覆盖主队战术字段，调用宿主序列化 TAC 内容，按 FMF v8 归档格式打包，并回读校验心态、球队指令、额外位域与两阶段单元四项一致后才返回文件。

存档页。主按钮改为导入存档文件，桌面端直接拉起原生选择器；删除要求手填 64 位哈希的新建存档与行内联赛球队 JSON 导入；每个存档行提供战术库展开区，列出存档内一线队存储战术的名称、风格、心态、槽位与可导入状态，可一键导入为战术草案并跳转战术板；阵容同步区保留应用名单到草案的能力。

战术板。草案支持新建、重命名、删除、复制；未保存离开有确认与浏览器卸载保护；空状态给出新建与导入 FMF 两个动作；心态可改，球队指令按运行时目录分组在内联下拉中编辑，旧版场景形态会说明两阶段各自保存并在保存后升级；导出真实 FMF，失败时按错误码给出设置页入口。

球员属性单项编辑。69 个属性格可直接输入，位置熟练度按 0–20 整数、其余按 1–20 显示值，唯一标记改动项并只提交这些项，保存失败保留编辑，切换球员、草案或主客队前确认放弃；批量覆盖折叠为高级工具，默认值不再预填，越界与禁用状态给出原因。

实验页。重排为选择战术、对比与场数、资源与提交三段，场数默认一百并给快捷值，可选基线做同种子 A/B 对照，自动拉取主机资源预填并行度并展示并发预检结论，提交后启动并跳转任务页；启动成功锁定表单，任务被占用时给出任务页与重新填写两条出口，失败按错误码分流到设置页或重试。

帮助与死控件。删除全局运行栏与任务页重复的新建任务表单，帮助页按真实能力说明三步上手、页面用途、有无引擎的能力边界与常见错误；所有禁用按钮写明原因。

## 四 后续计划

### P1 能力补齐

- 客队战术池管理界面，含条目权重与 FMF 条目导入。
- 职责、个人指令与盯人目标的完整编辑。
- 阵型模板与按位置自动排阵。
- 存档战术导出为 FMF 与加入客队战术池。
- 定位球编辑与导入导出。

### P2 体验打磨

- 实验进度显示已完成场数与预计剩余时间；任务重命名与筛选；结果页单场明细与失败场次解释。
- 响应式布局、焦点可见性、字号与对比度、加载骨架。
- 旧引擎目录在必需资源扩容后的迁移提示。

### 暂缓

存档对战按设计移除，不在本次恢复范围；桌面托盘与自检在发布前单独处理。

## 五 交互原则

每个页面只有一个主行动，其余操作按主次分层；任何禁用状态都必须在界面上写明原因与恢复方式；内部字段、原始路径、哈希与种子默认不出现在主流程，需要时放进折叠的高级区域；提交类操作给出进行中状态、结果位置与失败后的重试入口；能力依赖缺失时先解释缺什么、去哪配置，再提供跳转。

## 六 验收标准

新用户从打开应用开始，三分钟内完成导入存档、查看名单、应用名单到草案、编辑单个球员属性、跑一百场固定对手实验并查看结果，全程不需要手填路径以外的内部字段，不需要理解种子或并行度的含义，任何失败都有可读原因与下一步动作。

## 七 质量门

每个切片遵循测试先行、独立审核、全量回归：pytest、ruff、类型生成一致、前端 Vitest、类型检查、构建、源码清单匹配；审核子代理只读复核并做变异验证，结论 PASS 后才提交。
