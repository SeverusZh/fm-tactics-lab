# ADR-0011 取消意图的投递边界

- 状态：已接受
- 日期：2026-11-15
- 决策者：仓库维护者

## 背景

实验派发路径为 ExperimentService.start_next 置 running、检查取消事件、配置并行度、调用引擎 run_batch。原生宿主 NativeEngineHost.run_batch 在准备任务前清空自身取消标记，因此取消事件若在应用层检查之后、宿主清空标记之前到达，批次仍会跑完，而终态已经写成 cancelled。

修复前该竞态可稳定复现：取消落在检查之后导致 completed 等于 total 且状态为 cancelled。修复在派发前消费取消意图；随后评审发现 configure_workers 期间同步重入的取消仍会落入同一窗口。

## 决策

- 在 configure_workers 之后、run_batch 之前复检取消事件；已置位则直接写 cancelled，不派发批次。
- 取消意图由 ExperimentService 以每任务 Event 持有；引擎内部取消标记只服务于批次内部中断。
- 接受最后一次复检与宿主清空标记之间的指令级窗口：该窗口内到达的取消仍可能被吞，批次跑完且结果保留。彻底关闭需要取消令牌贯穿 EnginePort、真实宿主、懒加载包装与全部测试引擎，成本高于收益，桌面单用户场景也缺少稳定触发路径。

## 后果

- 派发前取消与配置阶段取消均不会启动引擎，终态 cancelled、结果为空。
- 极端竞态下仍可能出现批次跑完但状态为 cancelled 的组合；结果保留，用户看到取消。
- 并发矩阵用例覆盖检查前取消与配置阶段取消；真实引擎脚本以终态、逐场身份与吞吐为验收依据。

## 备选

- 取消令牌参数：需要改动引擎端口与所有实现，并重新定义跨批次语义。
- 宿主不清空自身标记：上一批次的取消会泄漏到下一批次。
- 不在应用层复检：配置阶段取消无法覆盖，评审指出的窗口保持原样。
