# ADR-0012 逐场释放标记的可见性与消费端等待

- 状态：已接受
- 日期：2026-11-16
- 决策者：仓库维护者

## 背景

counted-session 复用依赖逐场释放标记 `<output>.worker_done`：宿主写完该场输出后创建标记，应用层读到标记才把该场计入结果。真实宿主与假引擎都以“打开文件、写入 JSON、关闭”的方式创建标记，文件路径在内容落盘前即对其它进程可见。消费端原先在标记存在时只读取一次，读到空或半写内容就按无效标记处理。

CI 的 256 路矩阵因此偶发整批失败：某条分道读到不完整标记，`_run_chunk` 在 `retries=0` 且没有未完成场次时直接抛错，`run_batch` 取消其余分道并把整批写成 error；表现为已受理 246 场、结果序列缺少后 10 场、终态事件缺失。4 核绑定探针在 22 次中复现 3 次（达到 3 次即停止）。

## 决策

- 消费端对不可解析的标记做有界等待：宿主进程存活且未到 5 秒上限时视为 pending，按 20 毫秒轮询重读；宿主已退出或超窗仍不可解析则按无效标记失败。
- 无效标记的判定保持原语义：JSON 合法但 `released`、`exit_code`、`index` 不符时立即失败。
- legacy 源码版入口 `src/desktop_warm_batch.py` 使用同一等待逻辑。
- 写端不改为临时文件加 rename：真实宿主在 `native/desktop_host.cpp`，CI 无引擎资产无法回归该行为，改动风险高于收益；消费端等待覆盖同一可见性窗口。

## 后果

- 逐场标记在“路径可见、内容未落盘”窗口内不再被误判，256 路矩阵稳定通过；假引擎以 `partial_ack` 与 `garbage_alive` 夹具确定性覆盖该窗口。
- 宿主异常存活时最坏把无效标记的判定推迟到 5 秒上限；宿主已退出或标记合法时无额外延迟。
- 真实宿主的写端原子发布仍是有价值的改进，作为后续独立事项；在此之前以消费端等待为准。

## 备选

- 写端临时文件加 rename：原子性最好，但需要改原生宿主并在 Windows 真机回归，当前无资产。
- 只依赖进程退出后的 flush：无法覆盖宿主存活期间的正常读取，等待时间不可控。
- 把标记内容改为定长二进制或加长度前缀：仍无法避免“先创建后写入”的可见性窗口。
